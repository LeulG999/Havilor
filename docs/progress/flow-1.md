# Flow 1: Save one alert and read it back

**Goal:** `POST /api/v1/alerts` saves an alert with 4 fields; `GET /api/v1/alerts/{id}` reads it back. This is the
whole request pattern end to end: migration → entity → repository → service → DTO → controller → tests.

**Extra (senior) requirement:** **idempotency.** `ticketNumber` is unique, so sending the same alert twice never
creates a duplicate.

**Branch:** `feature/alert-save-and-read` · **Status:** done, 13 tests passing, pushed

## Decision: what the API returns for a duplicate

| Request | Status | Body | `Location` |
|---|---|---|---|
| `POST` with a **new** `ticketNumber` | **201 Created** | the new alert | `/api/v1/alerts/{newId}` |
| `POST` with a `ticketNumber` that **already exists** | **200 OK** | the **stored** alert, unchanged | `/api/v1/alerts/{existingId}` |
| `GET /api/v1/alerts/{id}`, found | **200 OK** | the alert | none |
| `GET /api/v1/alerts/{id}`, not found | **404 Not Found** | empty for now (Flow 3 adds the error format) | none |

**Why 200 and not 409 Conflict?** Alerts are sent by machines (the test generator now, MuleSoft later). They retry
when a response is lost or times out. A retry is **not** a mistake, so it shouldn't get an error. Returning the existing
alert means the sender can use the answer in the same way every time ("here is the alert for your ticket") and needs no
special error handling. The status code still tells it what happened: 201 = "I created it", 200 = "I already had it".

**Resending with different data** (same ticket, new subject): we return the stored alert **unchanged**. The first
version wins. Changing an alert is what `PATCH /alerts/{id}` is for (Flow 6). This is noted as a scoping decision. A
stricter API could answer 409 when the payload differs, and we can add that later if a real sender needs it.

## How idempotency works: two layers

```mermaid
sequenceDiagram
    autonumber
    participant S as Sender (generator / MuleSoft)
    participant C as AlertController
    participant SV as AlertService.create()
    participant R as AlertRepository
    participant DB as PostgreSQL (UNIQUE ticket_number)

    S->>C: POST /api/v1/alerts {ticketNumber, subject, receivedAt}
    C->>SV: create(request)
    SV->>R: findByTicketNumber(ticket)
    R->>DB: SELECT ... WHERE ticket_number = ?
    alt Layer 1: ticket already stored
        DB-->>SV: row found
        SV-->>C: CreateAlertResult(alert, created=false)
        C-->>S: 200 OK + Location + stored alert
    else not stored yet
        SV->>R: saveAndFlush(new Alert)  (own transaction)
        R->>DB: INSERT
        alt insert succeeds
            DB-->>SV: new row (id)
            SV-->>C: CreateAlertResult(alert, created=true)
            C-->>S: 201 Created + Location + new alert
        else Layer 2: another request inserted the same ticket first
            DB-->>SV: unique violation → DataIntegrityViolationException
            SV->>R: findByTicketNumber(ticket)  (fresh transaction)
            alt winner's row found
                SV-->>C: CreateAlertResult(winner, created=false)
                C-->>S: 200 OK + Location + winner's alert
            else no row: insert failed for another reason
                SV-->>C: rethrow the exception (→ 500 for now; 400 in Flow 3)
            end
        end
    end
```

- **Layer 1, the service check:** handles the normal retry cheaply, with no failed insert.
- **Layer 2, the database UNIQUE constraint:** the real guarantee. Two requests can both pass the check at the same
  instant (a **race condition**). Only the database can make sure one of them loses.
- **Why `create()` is not `@Transactional`:** if the insert failed *inside* an outer transaction, Spring would mark
  that transaction **rollback-only** and the Hibernate session would be unusable, so the re-read in Layer 2 would fail.
  Without an outer transaction, `saveAndFlush` runs in its own transaction (Spring Data repository methods are
  transactional by themselves) and the re-read runs in a fresh one. `findById()` *is* `@Transactional(readOnly = true)`.

## New concepts introduced

- **Request pattern end to end:** controller (HTTP only) → service (rules) → repository (DB) → entity; DTOs at the edge.
- **Flyway migration** `V1__description.sql`: versioned, runs once, recorded in `flyway_schema_history`. Never edit an applied migration; add `V2`.
- **JPA entity** (`@Entity`, `@Id`, `@GeneratedValue(IDENTITY)`, `@Column`) and why JPA needs a no-args constructor.
- **Spring Data derived query:** `findByTicketNumber` becomes `WHERE ticket_number = ?`, with no SQL written.
- **DTO as a Java record:** immutable, and keeps the database shape out of the API.
- **`Optional`** for "maybe there is no row" instead of `null`.
- **Idempotency:** the same request can be sent many times and the result is the same as sending it once.
  The **idempotency key** here is `ticketNumber`, the source system's own id.
- **Race condition** and why a check in code is not enough: **check-then-act** has a gap; the **DB unique constraint** closes it.
- **Transactions and failure:** a constraint violation inside a transaction makes it rollback-only, which is why
  `create()` has no outer `@Transactional`. `@Transactional(readOnly = true)` for reads.
- **HTTP semantics:** 201 Created + `Location` header vs 200 OK; 404 Not Found.
- **Test pyramid:** unit test (Mockito, fast, no DB) · slice test (`@DataJpaTest`, DB only) · integration test
  (`@SpringBootTest` + MockMvc, the whole app). A **concurrency test** with a `CountDownLatch` starts 8 requests at once.

## Scoping decisions (deliberately left for later flows)

- **No validation yet:** a missing `ticketNumber` causes a NOT NULL error, which is rethrown, so the caller gets a 500.
  Flow 3 adds `@NotBlank`/`@NotNull` + `@Valid` (400) and the global error handler with the `{status, error,
  message, path, timestamp}` format. The 404 body is empty until then.
- **`status` is a `String` (`"NEW"`)**; Flow 4 turns it into the `AlertStatus` enum.
- **Resent payloads are not compared** with the stored alert (see the decision above).
- The integration tests use the Docker database from `compose.yaml`; Flow 10 moves them to Testcontainers.
